# 4인 통합 회의

사용자가 정한 개발 사이클: **개발 → 전체 통합 회의 → 개선안 제시 → 개발 → 반복**
이 스킬은 "회의 → 개선안" 구간을 담당한다. 개발 투입은 `/round-start`.

## 1단계 — 병렬 검수 (한 메시지에서 4개 에이전트를 동시에 띄운다)

각 프롬프트 앞에 `.claude/agents/<이름>.md`를 먼저 읽고 그 역할로 행동하라고 지시한다.

| 에이전트 | 검수 범위 |
|---|---|
| `pm-integrator` | 요구사항 13개 대조표 + 전체 결함 목록 + 우선순위 |
| `web-designer` | 디자인 감사 — 가독성, 시선 흐름, 토큰 일관성, 다크모드, 모션, **계약서와 실제 코드의 괴리** |
| `frontend-dev` | 코어 감사 — 데이터 흐름, 렌더, 예외 4종, 보안(살균 경로), 날짜 규칙 |
| `frontend-dev-2` | 인터랙션 감사 — 에디터 유실 위험, 관리자 모드, 접근성, 모션 성능 |

모든 프롬프트에 반드시 넣을 문장:
> 파일을 실제로 읽고 `파일:줄`로 근거를 대라. 추측으로 말하지 마라. 확인 못 한 것은 "미확인"이라고 적어라. 결함을 찾는 것이 네 일이다 — 칭찬만 하는 보고서는 실패한 보고서다.

감사만 시키고 **이 단계에서 코드를 고치게 하지 않는다.** 회의 결과를 보고 우선순위를 정한 뒤 고친다.

## 2단계 — 교차 검증

네 보고서가 충돌하면 그대로 두지 않는다. 직접 해당 파일을 열어 누가 맞는지 판정하고 근거를 회의록에 남긴다.
특히 자주 충돌하는 지점:
- 디자이너는 "CSS에 있다"는데 개발자는 "클래스가 안 붙는다" → 실제 HTML/JS를 열어 확인
- 두 개발자가 서로의 파일을 원인으로 지목 → 호출 경로를 따라가 판정

## 3단계 — 회의록 작성

`docs/meeting-NN.md`로 저장(NN은 라운드 번호, 01부터).

```
# 라운드 N 통합 회의 (YYYY-MM-DD)

## 합의된 현황
## 요구사항 대조표 (13개 전부)
## 확정된 결함 (치명/중대/경미 순, 파일:줄)
## 판정이 필요했던 충돌과 결론
## 다음 라운드 작업 지시
### web-designer
### frontend-dev
### frontend-dev-2
## 사용자 결정 필요 사항
```

**작업 지시는 파일 소유권이 겹치지 않게 배분한다.** 겹치면 다음 라운드에 서로의 작업을 덮어쓴다.

## 4단계 — 사용자 보고

회의록 전문을 쏟지 않는다. **결함 요약 + 다음 라운드 할 일 5개 + 사용자 결정 필요 사항**만 간결히.
상세는 회의록 파일 링크로 안내한다.

## 금지 사항

- 서로 칭찬만 하는 회의는 실패한 회의다. 결함 0건이면 검수가 부실한 것으로 의심하고 다시 파고든다.
- 사용자가 요청하지 않은 기능을 백로그에 무한정 쌓지 않는다. 요구사항 충족과 품질이 먼저다.
- 외부 라이브러리 추가가 필요하다는 결론이 나오면 `/dep-request`로 **사용자에게 먼저 묻는다.**
