# 마크업 계약서 개정

`docs/contract.md`는 디자이너와 두 개발자가 동시에 작업할 수 있게 해주는 **단일 진실 공급원**이다. 계약서 없이 클래스를 추가하면 CSS는 있는데 HTML엔 없거나, 그 반대가 된다.

## 소유권

**계약서는 `web-designer`가 소유한다.** 개발자가 필요를 느끼면 요청하고, 디자이너가 판단해서 개정한다.
PM은 개정의 타당성을 검토할 수 있지만 직접 고치지 않는다.

## 개정 절차 (순서를 지킬 것)

### 1. 변경 이유를 한 문장으로
"필요해서"는 이유가 아니다. **어떤 화면의 어떤 문제를 해결하는가**를 적는다.
기존 클래스로 해결되지 않는지 먼저 확인한다 — 계약서가 비대해지는 것이 가장 큰 위험이다.

### 2. 영향 범위 조사 (개정 전에)
```bash
grep -rn "기존클래스명" css/ js/ *.html docs/
```
이름을 바꾸는 개정이면 **쓰이는 곳을 전부 찾아둔다.** 하나라도 놓치면 스타일이 빠진 요소가 생긴다.

### 3. 계약서 수정
해당 섹션에 새 마크업 블록을 추가하거나 기존 것을 고친다. 규칙:
- 클래스명은 기존 컨벤션을 따른다: 블록 `.memo`, 요소 `.memo-title`, 상태 `.is-active`
- 상태 클래스는 정해진 목록(`is-active is-open is-stuck is-hidden is-dirty is-loading is-pinned is-visible`)에서 고른다. 새 상태가 꼭 필요하면 그 목록에도 추가한다
- 토큰을 추가하면 토큰 섹션에도 반드시 등재한다
- 문서 맨 위 버전을 올린다(`v1` → `v2`)

### 4. 변경 요약 작성
개정 보고에 **변경 전 / 변경 후**를 나란히 적는다. 개발자는 이 diff만 보고 코드를 맞춘다.

### 5. 후속 작업 분배
| 변경 종류 | 후속 담당 |
|---|---|
| 새 컴포넌트 | 디자이너가 CSS, 담당 개발자가 마크업 |
| 클래스명 변경 | 디자이너 CSS + 해당 파일 소유 개발자 동시 |
| 토큰 추가 | 디자이너 단독 |
| 데이터 필드 추가 | frontend-dev(파서·렌더) + frontend-dev-2(에디터 입력) 둘 다 |

**데이터 필드 추가는 특히 주의한다** — 에디터에서 입력받지 못하면 사용자가 그 필드를 영영 못 쓴다.

### 6. 정합성 확인
개정과 구현이 끝나면 `/code-audit`으로 CSS↔HTML 클래스 정합성을 검사한다.

## 하지 말 것

- 코드를 먼저 고치고 계약서를 나중에 맞추기 → 이러면 계약서가 죽은 문서가 된다
- "일단 임시로" 계약서 밖 클래스 쓰기 → 임시는 영원히 남는다
